all_to_allMoE 的 dispatch/combine 对应算子，大消息下不劣于 all_reduce
小消息延迟 ~20 μs 解释了 EP2/TP4 中大量细粒度通信为何拖慢 step：accum=4 时每层多次小集合通信叠加。

highmem 档：只占 29%，不构成高显存压力（F11）

8 卡显存升到 40.7 GiB（29.0%） 后平台化， 未见泄漏式单调增长（growth≈0）；dmon 显示 SM 94.3%、功耗 642.4 W——就「跑 21 分钟不掉速」而言是稳定的。 但就「高显存压力」而言这档是无效的：峰值远低于 128K 短测的 137.3 GiB（97.8%），也低于 RUNBOOK 自定的 75% 下限， 按现行口径应判 WARN_LOW「未达高占用」，不能拿来回答「能否长期贴着显存上限跑」。

为什么会只有 29%：占用随 tokens/卡 线性增长

8B TP8 的静态占用（权重+梯度+优化器 16 B/参数 ÷ 8，加 NCCL/上下文）约 17 GiB，此后每 1K tokens/卡 约 +0.83 GiB： 16K→40.7、32K→53.1、128K→137.3 GiB。要落进 75~92% 的判定带需要约 97K~126K tokens/卡， 而该档只有 16K（mbs=1 × seq=16384）。反过来，脚本原默认 HIGHMEM_MBS=16（262K tokens/卡）约需 240 GiB，必然 OOM —— 「猜一个 mbs」本身不可行，这才是根因；现已改为在同一个模型上标定（见 F11）。
这里要校正一处口径：16K tokens/卡 在图上有两个点——torch max reserved 28.8 GiB（mbs4×seq4096 短测）与 nvidia-smi 峰值 40.7 GiB （mbs1×seq16384 的 21 分钟长稳），指标和 seq 都不同，不能相减。能算漂移的只有同配置同指标： 4 步试跑 35.6 GiB（25.4%） vs 21 分钟长稳 40.7 GiB（29.0%） → +5.1 GiB ≈ +3.6 个点。 标定按 +8 点留保守余量（HIGHMEM_DRIFT，选档带 75~84%，判定带 75~92%）。

⑨ 结论与可执行建议

性能结论 + 按优先级排列的修复清单

性能天花板
最优档 tp1_pp1_mbs2_s4096_gb32_bf16 达 519.5 TFLOP/s/GPU（MFU 52.5%），靠 DP8 无 TP 通信 + 每卡 16K tokens 的大 GEMM；代价是显存 92.8 GiB。
TP 不是越大越好
同配置 TP1→TP4→TP8 吞吐 519.5→418.3→313.4（-39.7%），但显存从 92.8 降到 17.2 GiB（-81.5%）。TP8 的价值在长序列/大模型的显存可行性，而非算力效率。
序列长度拐点
TP8/GBS8 下 2K→32K 吞吐从 96.8 升到 398.6，128K 回落到 316.8（-20.5%），单步 61,282 ms、显存 137.3 GiB（≈98% 容量）；32K 是吞吐拐点，128K 不建议作为生产档。
MoE 拓扑决定一切
EP8/TP1 的 177.6 TFLOP/s/GPU 是 EP2/TP4（37.7）的 4.7 倍；dispatcher 影响仅 2~12%。EP2/TP4 需 4 次梯度累加（accum=4）是主要损耗来源。
长稳表现分化
Dense 2h 12,503 步 CV 2.51%、漂移 +0.12%、0 慢步、SM 97.3%、功耗 643.9 W，健康零增量；MoE 30min 漂移 +11.2%、CV 6.87%、20 个慢步，且缺专家负载数据，需补测后才能判定稳定性。
显存边界
MOE_B 静态占用 84.7 GiB / 卡容量 139.8 GiB，余量 55.7 GiB；mbs4@4096 与 mbs2@8192 同为 16,384 tokens/GPU 均 OOM，边界由「每卡 token 数」而非 mbs 或 seq 单独决定，位于 8K~16K tokens/GPU。

数据口径说明

1. 稳态指标：解析每个训练日志的 iteration N/15 | elapsed time per iteration (ms) | throughput per GPU (TFLOP/s/GPU)，剔除第 1 步（初始化）与第 15 步（收尾），取中间 13 步的中位数；长稳段剔除前 20 步与末 5 步后统计。
2. MFU（本次修订） = Megatron 日志 throughput per GPU (TFLOP/s/GPU)（模型有效 FLOPs，6ND 口径）÷ H200 SXM BF16 Tensor Core dense 理论峰值 989.5 TFLOP/s。NVIDIA 规格表的 1979 TFLOPS 标注「with sparsity」，稠密训练须取一半。04-hw 实测 GEMM 690 TFLOP/s 仅为理论峰值的 69.7%，属于「本机可达上限」，以它为分母会把 MFU 放大 1.434 倍；首版报告误用该口径，现全部废弃，旧值 × 0.697 = 新值。反推 moe.jsonl 的 mfu_active 也证实项目自身分母为 989.5。注意 Megatron throughput 与 GBS×seq 成正比，跨 GBS/seq 比较须同时看 accum 与 tokens/GPU；且分子不含重计算，启用 recompute 时实际硬件利用率（HFU）会高于此处 MFU。
3. 显存：取日志 max reserved (MB) 的最大值并按 1024 换算为 GiB；GPU 容量来自 04-hw 的 cap_gib=139.8。
4. 硬件探针修正：NCCL busbw = 原始 busbw_gbs × iters（少除）；HBM / PCIe = 原始记录 ÷ 饱和 iters（500 / 50，多乘，属估算）；latency_us 为单次通信耗时，未作修正。bf16 GEMM 公式无此问题。两处公式已修（F3 / F10），但本历史 run 的数值仍按上述修正口径展示。
5. 状态：OOM_BOUNDARY 按 limit-summary.json 约定为预期边界，不计失败；未标记 .ok 的 soak 段视为未完成。
